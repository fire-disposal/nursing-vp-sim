## 二、并发承载力评估

当前架构 **最大承载约 20-30 并发学生同时训练**：

- 每个训练会话约 1 个长连接 SSE 流 + 周期性评分调用
- 后端单进程 ~130MB，`_MAX_REQUEST_BYTES=10MB`，TaskQueue 3 workers
- LLM 并发限制 `LLM_CONCURRENT_LIMIT=50`
- 瓶颈在 **DeepSeek API 响应延迟**（聊天 ~1-2s，评分 ~13s），而非服务器 CPU
- 若 30 人同时聊天，最多同时 30 个 SSE 连接 + 15 个评分排队
- **结论：够用**。一所护理学校单班约 40 人，现实场景不会全班同时在线训练

## 四、交付评估

**当前状态：可交付给内部测试用户 (alpha)**，接近「维护模式」就绪。

**差距分析**：要让一个微企业接手并进入「只修 bug、不改功能」的维护模式，还需：

1. **P0 剩余 2 项** (~3 hr) — messages IntegrityError + 数据库备份
2. **P1 至少修完 #5-#8** (~10 hr) — 基础用户体验
3. **P1 微信小程序视需求定** — 如果学生用微信入口，则必做
4. **至少一条完整的端到端验收测试** — 从登录->选Practice->训练->评分->教师复核->导出报告

**预估剩余工作量：P0+P1(除小程序) ~13 工时**，即可达到「维护模式」状态。加上小程序约 21 工时。
