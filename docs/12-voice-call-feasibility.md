# 12 — 电话式纯语音采集（A 形态：应用内通话）可行性论证

> 状态：论证文档（非决策）。2026-07-31 基于当前主干代码盘点。
> 范围：A 形态（应用内通话，类似微信语音）的技术路径、现状盘点、工作量与风险评估。
> 明确不做：B 形态（真实 PSTN 电话，监管 + 号码资质）；全双工语音二期排期。

---

## 一、执行摘要

在现有训练系统上实现"打电话"式纯语音病史采集，**单人 3-5 周可出教学闭环可用的 MVP**，前提是：

1. 明确 MVP 边界 = **半双工对讲机模式**（无打断、无全双工、无真实电话）。
2. ASR 输入端从零接入（当前系统只有 TTS 输出端，无任何语音识别实现）。
3. 转写文本复用现有 chat SSE 管线，评分链零改动自动覆盖。

教学价值判定：**价值在"语音输入 + 自动评分"闭环，不在"像不像真电话"**。半双工模式已覆盖 90% 的教学价值。

## 三、三种形态辨析

| 形态 | 本质 | 技术难点 | 教学场景适配 |
|------|------|----------|--------------|
| **A. 应用内语音通话** | 浏览器内全双工/半双工对话（类似微信语音） | 低-中：ASR + turn-taking + 可选打断 | ✅ 电话随访/接诊训练，可记录可评分 |
| B. 真实 PSTN 电话 | 学生拨真实号码，系统接听 | 高：号码资质 + 电信接入 + 录音合规 | ❌ 模拟训练不需要真实号码，监管无底洞 |
| C. 半双工对讲 | 按住说话 → 患者语音回复 | 最低：无打断、无并发 | ✅ 就是 A 的 MVP 形态 |

**选择**：A 形态的 MVP 实现即 C 形态（半双工）。B 形态明确不做。

## 四、主流技术路径

```
┌─────────────────────────────────────────────────────────────┐
│ 路径 1：托管语音 Agent 平台（最快，2-4 周）                  │
│   火山引擎·豆包语音 Agent / 阿里云百炼·通义 / 讯飞星火      │
│   └─ 平台内建: ASR + LLM + TTS + VAD + barge-in + 打断      │
│   └─ 代价: 现有火山 TTS/DeepSeek 路由/审计被平台接管         │
├─────────────────────────────────────────────────────────────┤
│ 路径 2：开源全双工框架 + 现有组件（4-8 周）                  │
│   LiveKit Agents / Pipecat / FireRedChat                    │
│   └─ 框架管: 会话编排、VAD、打断、WebRTC                    │
│   └─ 你接入: 现有火山 ASR/TTS + DeepSeek + TrainingAction    │
├─────────────────────────────────────────────────────────────┤
│ 路径 3：自建 MVP（3-5 周）◀── 本文推荐                        │
│   浏览器 getUserMedia + SpeechRecognition + 现有 SSE/TTS     │
│   └─ 半双工: 学生说 → 转写 → 现有 chat 管线 → 患者回复 TTS  │
└─────────────────────────────────────────────────────────────┘
```

**推荐路径 3 起步，路径 2 作为二期升级**：

- 路径 1 把现有火山 TTS 能力和评分系统关在平台黑盒里，破坏审计链，不选。
- 路径 3 只写前端会话层，后端零改动，最快验证教学闭环。
- 识别质量成为瓶颈后切路径 2（LiveKit/Pipecat）或自建全双工，会话层接口提前隔离。

## 六、关键风险

### 6.1 ASR 识别质量（最大变数）

- 浏览器内建 `SpeechRecognition`：免费、零后端、零延迟，但依赖 Chrome/Edge，医学名词（"他汀类"、"呼吸困难"）易错。
- 火山 BigASR：质量好、可加热词表，但需要恢复 ASR 配置列（迁移曾删除）并自建后端 WS 客户端。
- **建议**：MVP 用浏览器方案免费验证教学闭环；识别质量成为瓶颈时切火山，切换点用接口隔离。

### 6.2 打断（barge-in）

- 学生在患者说话时插话 → 需停 TTS、丢弃未说完内容、切回聆听。
- `TTSManager.stop()` 已存在；前端可监听麦克风 VAD 触发。
- **MVP 可先不做**（半双工：患者说完才可说话），体验降级但闭环完整。打断归二期。

### 6.3 资源消耗（已有资金支持，记录备案）

| 项 | 单价估算 | 对比文字采集 |
|----|----------|--------------|
| ASR | ~¥0.005-0.01/分钟（BigASR）或 ¥0（浏览器方案） | — |
| TTS | ~¥0.01-0.02/分钟 | 相同 |
| LLM | ~15-25 轮/分钟 × 512 tokens ≈ ¥0.01-0.03/分钟 | 3-5 倍 |
| **合计** | **~¥2-4/小时** | 3-5 倍，非量级差异 |

瓶颈不在钱，在**体验质量**（打断识别、延迟 <1s、医学名词转写）。

## 七、结论与建议

```
✅ MVP（3-5 周，单人可做）：
   A 形态简化版 = 对讲机模式
   麦克风录音 → 浏览器 ASR → 转写文本走现有 chat SSE
   → 患者回复自动 TTS 朗读
   （无打断、无全双工、无真实电话）

⏸ 二期（资金到位后）：
   全双工 + barge-in + VAD → LiveKit Agents 或 Pipecat
   识别质量打磨（火山 BigASR + 医学热词表）

❌ 明确不做：
   真实 PSTN 电话（监管 + 号码 + 录音合规）
   全双工语音（工程复杂度量级提升）
```

**关键洞察**：教学闭环的价值不在"像不像真电话"，在"语音输入 + 自动评分"。对讲机模式已覆盖 90% 的教学价值，且只需一个前端会话 hook + ASR 接入，后端训练/评分链零改动。
