# 16 — 可维护单体：持久架构约束

> 更新：2026-09-27。本文只定义长期架构边界，不定义发布顺序或产品下一站。
> 当前训练计划见 [19](19-training-experience-next-generation-plan.md)，临床推理去向见 [18](18-clinical-reasoning-disposition.md)，实现契约见 [15](15-workflow-activity-contract.md)，身份命名见 [17](17-training-identity-and-state-contract.md)。
> 旧 M0–M4、M2.5 第二闭环、重复的重构待办及未执行技术预研已删除，不再作为实施依据。

## 一、总决策

单人维护的实验性训练系统，不做技术栈重写、微服务化或通用插件平台。以可理解、可修改、可验证、可恢复的真实训练路径为目标，不以层数和抽象数量为成果。

1. 一个事实只有一个权威写入 owner。
2. 没有真实消费路径，不提前建设 SDK、通用 DSL 或扩展平台。
3. 代码导航沿 router → 业务服务 → 模型/外部依赖，不增加平行分层。
4. 状态对用户诚实；能自助恢复的失败不能伪装成成功。
5. 规范化与科研追踪复用现有记录，不借此扩张安全合规产品。

## 二、技术栈边界

| 部分 | 保留 | 不做 |
|---|---|---|
| 后端 | Python / FastAPI 可导航单体 | 全栈重写、拆微服务 |
| 数据 | PostgreSQL、SQLAlchemy、Alembic | 为本批训练引入 Redis/Kafka、多数据库 |
| 前端 | React / Vite、Mantine | Next.js 迁移、第二套 design system |
| 状态 | 服务端数据由 Query 管理；客户端工作区/瞬态由现有状态层管理 | 第二套业务状态源 |
| 通道 | HTTP 查询/工具命令、SSE 对话、WS 服务端推送 | WS 业务写入旁路 |
| 部署 | 单实例 Docker Compose 与现有 CI/CD | Kubernetes、多实例产品化 |

参数、运行角色与端点以代码和部署配置为准。本文不复制容易过期的配置表，也不承诺独立 worker 已运行。

## 三、正式训练闭环边界

正式训练围绕病例发布、受众、对话/查体、护理评估提交、评分、教师复核展开。下一代还需让学生看到反馈并完成再练习与迁移，范围由 19 决定；原“最小闭环”不是阻止深化的上限。

`clinical_reasoning` 与独立 simulations 不接入本批次闭环。保留冻结实验资产不是删除死代码的普遍授权；其去向由 18 单独裁定。

## 四、后端与持久化约束

- 保持 `core/`、`models/`、`schemas/`、`modules/`、`infra/` 的可导航单体组织；具体导航见 [11](11-backend-organization-plan.md)。
- 同步 ORM 不做全量异步迁移；数据库密集路径明确线程/同步边界，外部 LLM 调用期间不持有长事务。
- 聊天回合区分写入学生消息、外部调用、写入患者结果，失败与恢复状态可辨。
- 可恢复后台任务必须有持久状态、失败原因与恢复机制；不把进程内进度字典当作跨进程事实。是否拆独立 worker 必须由实际恢复/负载需求驱动，不是预定里程碑。
- 正式产物、证据、复核和长期回放所需事实有持久 owner；`runtime_state` 不作为正式结果旁路。
- 病例与训练快照不可变；编辑发布新 revision，缺失历史不能用今天的内容冒充原内容。
- 生产迁移沿现行部署流程执行；禁止把恢复测试、建表或破坏性重置作用于用户数据库。

## 五、前端与契约约束

- 训练主链由 `TrainingEntry` / `TrainingEngine` 与现有工作区承载，不新增平行前端架构。
- 页面组合、组件呈现、API 模块请求；服务端 manifest 决定活动、产物与完成条件。
- 自动生成的 API 类型通过仓库命令更新；契约变化迁移所有消费方，不留下双写兼容层。
- 保存、评分、断线与计时提示来自实际状态；不得用定时器或假百分比宣布业务成功。
- 历史读取可保留必要解释分支，但新功能只有一条权威写入路径。

## 六、评分与研究约束

原始行为判定、量尺、展示分、能力等第、教师复核分开建模。算术正确不证明教学有效；版本字符串相同不证明历史量尺相同。

不静默覆盖旧成绩，不倒推伪造原始项，不混合不可比量尺做进步结论。校准与历史解释统一按 19 W0/W4，不在架构层预设“优秀=某个硬编码数字”。

## 七、变更准入

每个实现工作必须能回答：改变了哪条用户路径、由谁拥有事实、失败如何可见和恢复、哪些消费方需要一起迁移、用什么实际场景验收。

纯抽象、目录搬迁、测试数量增加或增加可配置项不单独构成产品进展。只有明确负载、恢复或教学需求出现，才考虑新基础设施和新工作流。

## 八、架构验收判据

- 学生和教师能完成实际训练、结果读取与复核路径，而不只是 API 返回成功。
- 提交、完成、评分和复核不能产生对用户不可解释的半写状态。
- 后台失败与流式中断有确定状态和恢复路径；未知进度不伪造。
- 同一事实无竞争 owner；冻结历史不被新规则覆盖。
- 发布与回滚可按当前运维规程执行；tag 自动部署不等于获得发布授权。
- 当前产品验收同时满足 [19](19-training-experience-next-generation-plan.md)，本节不能替代教学校准。
