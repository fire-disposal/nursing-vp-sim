# 16 — 2.0 可维护单体与最小产品闭环目标

> 状态：当前决策（2026-09-25）
> 维护前提：单人维护，同时负责产品、前后端、CI/CD、部署、数据与线上运维。
> 本文件是 2.0 的当前约束与目标，不是无限扩张的功能路线图。
> 旧的路线规划、重构分域计划与未执行的技术预研不再作为实施依据。

## 一、总决策

2.0 不做技术栈重写，不做微服务化，不做通用插件平台。目标是把已经通过预实验与机房测试的系统，收敛成更容易被单人和编程 Agent 导航、修改、验证与回滚的可维护单体。

目标架构：

```text
React/Vite SPA
      ↓ HTTP / SSE
FastAPI 可导航单体 ───── PostgreSQL
      │                      │
      └──── API + Worker ─────┘
             （同一代码、同一镜像、不同运行角色）
```

核心原则：

1. **可靠路径优先于扩展性叙事**：只为真实学生、教师、评分和运维路径保留代码。
2. **一个事实，一个 owner**：状态、产物、评分、权限、配置都只能有一个权威写入路径。
3. **先减法，再抽象**：没有第二个真实消费者，不保留 registry、SDK、通用 DSL 或兼容分支。
4. **实时请求与后台任务分离**：聊天实时返回；评分、导出、通知等可恢复任务进入持久化 job。
5. **文档服务导航，不替代代码**：文档只记录现行入口、边界、验收与运维动作。
6. **每个改动必须有用户或运维结果**：单纯增加层次、类型、目录或测试数量不构成产品进展。

## 二、当前技术栈取舍

| 部分 | 2.0 决策 | 不做的事 |
|---|---|---|
| Python/FastAPI | 保留 | 不换 Django、Go、Node，也不拆 API 服务 |
| SQLAlchemy 2 + Alembic | 保留同步 ORM；修正 async endpoint 的阻塞边界 | 不做全量 Async ORM 重写 |
| PostgreSQL | 保留；同时承载交易数据与轻量持久化 job | 不引入 Redis/Kafka 作为必需依赖 |
| React 19 + Vite | 保留 | 不迁 Next.js，不重建 SPA |
| TanStack Query + Zustand | 保留分工：服务端状态 / 客户端瞬态 | 不再增加第二套状态管理 |
| Mantine | 保留唯一 UI 组件体系 | 不增加另一套 design system |
| HTTP + SSE | HTTP 做查询/命令，SSE 做聊天流 | 不把聊天改造成 WebSocket 业务协议 |
| Docker Compose | 保留单实例；增加同镜像 worker 运行角色 | 不上 Kubernetes |
| GitHub Actions | 保留；区分快速门禁、迁移门禁、发布门禁 | 不新增独立 CI 平台 |

## 三、最小产品闭环

2.0 第一交付目标只有一条：

```text
教师创建并发布病例
  → 学生进入训练
  → 病史采集对话
  → 床旁检查
  → 护理评估
  → 保存草稿
  → 显式提交并冻结
  → 完成训练
  → 评分
  → 教师查看 Artifact、证据与复核结果
```

### 必须收敛的功能

- 护理诊断并入护理评估 Artifact；不再新增独立的 runtime_state 旁路写入。
- `NursingRecord` 是护理评估与诊断的正式产物；未提交内容不得进入正式评分。
- `physical_exam` 保留为确定性活动，结果进入 `TrainingAction` / 评分证据。
- Quiz 暂作为非阻塞辅助能力；未完成 Artifact、评分和复盘闭环前，不扩大它的产品承诺。
- 学生端只围绕“对话、床旁检查、护理评估、完成”组织主界面。
- 教师端只优先保证“病例发布、作业受众、训练结果、复核下钻”。
- 演示、实验、未接入生产闭环的路由必须有明确开发环境边界，不进入生产导航。

### 明确不进入第一闭环

- `clinical_reasoning` 第二 Workflow 产品化（**不在第一闭环内**；已确认的形态与切片顺序见 §七 M2.5）；
- 动态插件加载、插件市场、版本协商；
- 通用 Context/Evidence 平台；
- 全量语音电话产品化；
- 视频患者表现层；
- 面向未来的多租户、分布式部署或事件溯源。

## 四、后端结构调整

### 4.1 保留可导航单体

```text
backend/
  core/       配置、数据库、鉴权、异常、事务、限流
  models/     ORM 与全局数据模型
  schemas/    API 契约
  modules/    产品领域
    training/ 唯一复杂业务岛
  infra/      LLM、TTS、任务、诊断、外部系统
```

不新增 `repositories/`、`domain/`、`application/`、`use_cases/` 等平行分层。训练域内部可以按实际流程分文件，但每个入口必须能从 router 或训练域地图直接找到。

### 4.2 实时请求与后台任务分离

当前进程内 `asyncio` 队列适合实验，不适合作为评分和导出的唯一可靠存储。2.0 引入最小 PostgreSQL job 表：

```text
pending → running → succeeded / failed
```

job 至少记录：`kind`、`payload`、`attempts`、`available_at`、`locked_at`、`last_error`、`finished_at`。

优先迁移：

- 评分；
- 导出；
- 批量通知；
- 可重试的后台同步。

聊天生成仍保持实时 SSE，不转成后台 job。

### 4.3 迁移不再由生产应用启动执行

生产发布顺序固定为：

```text
备份 → Alembic upgrade head → 启动/重启 API 与 worker → health/diagnose 冒烟
```

应用启动只验证 schema 状态，不负责和多个 worker 争抢迁移锁。`create_all` 仅允许测试或临时环境使用。

### 4.4 JSONB 与运行态边界

普通列负责：

- 状态机状态；
- revision；
- 时间与并发版本；
- 查询和排序字段；
- 评分状态。

JSONB 负责：

- 冻结病例快照；
- prompt/rubric 快照；
- 正式 Artifact 内容；
- 不需要跨记录聚合的结构化产物。

`runtime_state` 只保留：

- 情绪瞬态；
- 主动追问状态；
- 临时会话标记；
- 恢复所需的运行状态。

任何教师复核、正式评分或长期回放所需事实，都必须进入正式表或冻结 Artifact。

### 4.5 async 与同步 ORM 边界

不进行全量 Async SQLAlchemy 迁移。采用简单规则：

- 数据库密集、非流式 endpoint 使用普通同步 endpoint 或明确线程边界；
- LLM/SSE 才使用异步路径；
- 不在长时间外部调用期间持有数据库事务；
- Chat 采用“事务 A 写入学生回合 → 外部 LLM → 事务 B 写入患者回合”的边界。

## 五、前端结构调整

不做全量目录迁移，只做可导航收敛：

1. `engine/` 是训练运行时唯一入口；
2. `components/training/` 是训练 UI 唯一业务岛；
3. `api/` 是后端契约访问入口；
4. TanStack Query 保存服务端状态；
5. Zustand 只保存工作区、草稿、流式和 UI 瞬态；
6. 生成的 OpenAPI 类型不手改，不再新增同名视图类型；
7. 页面负责组合，组件负责呈现，API 模块负责请求；
8. 删除死 barrel、死路由和无读取方的兼容层；
9. 训练主链必须能从 `TrainingEngine`、聊天入口、工具入口和评分入口分别导航到完整调用链。

不为“看起来企业化”引入 `features/` 全量迁移或第二套前端架构。

## 六、推荐的代码精简

按价值优先级处理：

### P0：影响正确性或恢复

- 生产迁移移出应用 startup；
- 评分、导出任务持久化；
- 所有正式产物统一 owner；
- 评分、复核、完成状态保持单事务语义；
- 删除生产路径中无消费者的演示/调试路由；
- 统一 LLM 成本、错误、重试和降级记录出口。

### P1：影响 Agent 导航和改动风险

- 每个复杂域补一份入口地图，而不是新建抽象层；
- 删除旧 `training_type`、空 registry、死类型、死 barrel、失效 compatibility alias；
- 统一 `utils/lib`、前端重复类型、训练 hook 归属；
- 把超大页面按业务阶段拆分，不按“Manager/Helper/Util”拆分；
- 把运维诊断字段和业务状态字段分开。

### P2：体验和运营顺手改进

- 学生明确看到“草稿 / 已提交 / 可完成 / 阻塞原因”；
- 教师列表显示“未开始 / 进行中 / 已完成 / 待复核 / 评分失败”；
- 评分失败必须可重试、可解释、可诊断；
- 发布前展示受众快照和病例版本；
- 移动端完成训练、提交评估、重试评分不依赖隐藏面板；
- 所有危险操作保留确认、结果反馈和可回溯状态。

## 七、推荐发布切片

### M0：边界冻结

- 删除或废止旧路线规划文档；
- 记录当前 2.0 目标；
- 停止新增平台化抽象；
- 建立“核心用户路径 → 代码入口 → 数据 owner”地图。

### M1：运行时可靠性

- job 持久化；
- 生产迁移移出应用启动；
- worker 独立运行；
- 诊断端点可观测 job、评分和 LLM 降级；
- 重启后后台任务可恢复。

### M2：训练闭环

- 对话、床旁检查、护理评估、完成、评分、教师复核贯通；
- 护理诊断并入护理评估 Artifact；
- 学生和教师各有一条真实浏览器验收路径。

### M2.5：第二闭环 —— 临床判断训练（Clinical Judgment Drill）

已确认的产品形态：**独立的临床判断训练 Activity**，单次 15–20 分钟，阶段链为
「发现线索 → 聚焦评估 → 获取证据 → 判断 → 行动 → SBAR → 复评」，产出结构化推理产物并接受
确定性评分与教师复核。它不是第二套聊天、也不是 RPG：**共享** Session 身份、`CaseRevision`、
`Assignment`/受众、`TrainingRecord`、Artifact/Evidence、`Score`/复核与教师查询框架；
**独立**阶段工作流、证据形状、评分 rubric 与工作区 UI。

切片顺序（每片独立可验收，未落地前不进生产导航）：

1. **判别契约（Slice 0，已完成）**：`CaseRevision` 决定 workflow → `training_records.workflow_id`
   冻结 → 运行期一律 `workflows.workflow_for_record(record)`；客户端不能选择 workflow；
   病例门禁与解析器双层拒绝未登记 workflow。见 `docs/15 §十六`。
2. **结构化五阶段推理产物**：`clinical_reasoning` 闭包登记 + 阶段状态机 + 结构化推理产物
   （draft → submitted 冻结），进入 completion 与复盘。
3. **确定性证据与 rubric**：证据取自 `TrainingAction` + 已提交产物 + 终局判定；能算的不用 LLM 判；
   rubric 与该 workflow 绑定，不与护理评估共享维度。
4. **教师证据时间线**：行动 → 证据 → 判断 → 评分依据可下钻，复用既有复核队列框架。

约束：不新增第二套发布/受众/评分/复核体系；不复制一遍外围（第三个 workflow 出现时不应再复制）。
仍然**不做**动态插件加载、插件市场、版本协商、通用 Context/Evidence 平台。

### M3：减法与可导航性

- 清理死代码、死路由、死类型和重复契约；
- 训练域入口地图完成；
- 前端页面按业务阶段收敛；
- 文档只保留当前架构、运维和验收要求。

### M4：基于数据决定是否扩展

只有出现明确运行指标后，才评估 Redis、独立服务、多实例、Async ORM 或 LLM gateway。技术选择必须由吞吐、任务堆积、故障恢复或安全要求触发。

## 八、2.0 验收标准

### 产品

- 教师可以发布病例和受众；
- 学生可以完成一条训练闭环；
- 护理评估与诊断提交后可回放；
- 正式评分只读取冻结 Artifact；
- 教师能看到评分依据和复核结果。

### 可靠性

- API 重启不丢失已领取的后台任务；
- 任务失败有状态、原因和重试入口；
- SSE 中断后回合状态可恢复或明确失败；
- 评分、复核、完成不产生半写状态。

### 可维护性

- 核心路径不依赖未来插件平台；
- 新 Agent 可以从一个入口文件找到业务主链；
- 同一事实没有多个写入 owner；
- 发布、迁移、回滚和诊断动作在文档中可直接执行；
- 每个 2.0 commit 都对应可观察的用户或运维结果。
