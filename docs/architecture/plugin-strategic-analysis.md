# 插件系统战略分析 — 从架构与产品视角的演进方向

> 作者视角: 技术决策者 / 产品负责人
> 审查范围: 系统全局架构、业务领域模型、产品演进路线
> 日期: 2026-06-17

---

## 前言

这不是一次代码审查。在铸造工坊里，我们不能只盯着齿轮的齿纹是否精细，更要问——这台机器的传动结构是否合理？它要解决的真问题是哪个？十年后它还能转吗？

第一份报告回答了"插件系统现在怎么样"。这份报告要回答的是：**插件系统应该往哪里走，以及为什么。**

---

## 一、还原问题本质：插件系统要解决的到底是什么？

先放下代码，回到产品需求的原点。一个护理虚拟患者模拟系统的核心复杂性不来自技术，而来自**领域模型的多样性**。

### 1.1 正确的命题

系统中存在两种不同的"可变性"：

| 变化类型 | 例子 | 变化频率 | 预期管理方 |
|---|---|---|---|
| **教学配置变化** | 不同护理病例有不同的问诊要求、查体项目、评估阶段 | 每次创建新病例 | 教师/内容管理员 |
| **功能特性变化** | 是否启用情绪模型、是否启用主动追问、是否允许暂停 | 每次训练或每学期 | 教师/教学主任 |

这两种可变性在经典架构中应当通过**配置驱动**而非**代码扩展**来解决。当前的插件系统试图用一个机制解决两个问题——但实际上是两个正交的问题。

### 1.2 错误的解法

插件系统将"功能开关"和"代码扩展点"混为一谈：

- `emotion` 插件 = 一个功能开关（是否启用情绪模型）+ 一个代码扩展点（中间件）
- `nursing-record` 插件 = 一个 UI 注册项（"给我一个 Tab"）
- `questionnaire` 插件 = 一个 overlay 注册项

前者是**运行时常量**，后者是**编译时扩展**。塞进同一个机制导致两个抽象都不纯粹。

### 1.3 谁需要插件？

关键问题：**未来的扩展方是谁？**

- 如果是**本团队**继续开发 → 不需要插件系统，直接写核心模块更快、更安全、更容易测试
- 如果是**第三方开发者**接入 → 需要成熟稳定的 SPI（Service Provider Interface），而不是目录扫描 + 按照约定发现插件的半成品
- 如果是**教学管理员配置新病例** → 需要后端配置系统 + 前端动态面板渲染，不需要编写代码

当前的插件系统没有明确回答这个问题，因此处于"两边都够不着"的灰色地带。

## 二、系统架构分析

### 2.1 当前架构的三个断层

```
┌──────────────────────────────────────────────────────────┐
│                    前端 React 渲染层                        │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐     │
│  │emotionTab│ │examPanel │ │inquiryTab│ │nurseRec  │ ... │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘     │
│       │            │            │            │            │
│  ┌────┴────────────┴────────────┴────────────┴─────────┐  │
│  │            PluginRegistry (运行时注册)               │  │
│  │   import.meta.glob 扫描 → 发现 → 按 flag 过滤      │  │
│  └───────────────────────┬─────────────────────────────┘  │
│                          │ HTTP                           │
└──────────────────────────┼────────────────────────────────┘
                           │
┌──────────────────────────┼────────────────────────────────┐
│                  后端 FastAPI 层                           │
│  ┌──────────────────────┴─────────────────────────────┐  │
│  │            PluginManager (运行时扫描)               │  │
│  │   importlib 扫描目录 → discover → register         │  │
│  └────┬───────────────────────────────────┬───────────┘  │
│       │ middleware                        │ routes       │
│  ┌────┴──────────┐               ┌────────┴───────┐     │
│  │pipeline chain │               │perform_exam     │     │
│  └────┬──────────┘               └────────────────┘     │
│       │                                                  │
│  ┌────┴──────────────────────────────────────────────┐  │
│  │             核心业务层 contexts/patient/            │  │
│  │   emotion.py  exam.py  initiative.py  guards.py    │  │
│  └───────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**断层一：前端恐慌式扫描**

`import.meta.glob("@/plugins/*/index.{ts,tsx}")` 全量加载再过滤。无显式依赖树、无懒加载、无类型检查。每次前端启动都要遍历文件系统、加载所有插件模块、再根据 manifest 过滤。这在 8 个插件的规模下不是问题，但一旦扩展，冷启动和构建都会受到影响。

**断层二：后端插件层空转**

`PluginManager` 的管理流程：
1. 启动时扫描目录，import 所有 `plugins/*/plugin.py`
2. 实例化插件类
3. 运行时再次根据 flag 过滤
4. 为每个请求动态组装 pipeline

实际效果：**一半的插件类没有提供任何中间件、路由或 hook**。它们的存在仅仅是为了让前端知道 "我有这个 UI"。

**断层三：后端做前端注册的事**

为什么后端的 Plugin 类要声明 `ui_manifest()`？前端的 Tab 注册完全可以在前端完成，不需要后端通过 API `/api/plugins/manifest` 下发——尤其当插件的 flag 和依赖验证逻辑在前端 PluginRegistry 里又复制了一遍：

```typescript
// 后端 Python
if plugin.feature_flag is not None:
    flag_key = ff.key
    if not flags.get(flag_key, ff.default): return False

// 前端 TypeScript（完全相同的逻辑）
if (mp.feature_flag !== undefined) {
    if (!flags[mp.feature_flag]) return false;
}
```

这个双端验证表名所花费的维护成本 > 它所提供的价值。

### 2.2 认知复杂度分析

从开发者的视角看当前系统的认知负担：

| 维度 | 当前 | 理想 |
|---|---|---|
| 要理解一个功能如何工作 | 需追踪: 插件类 → middleware → core 模块 → NoteSource → manifest → 前端组件 | 只需追踪: config → core 模块 |
| 要新增一个功能 | 创建目录 → 写 plugin.py → 写 middleware → 注册 route → 创建前端组件 → 建索引 | 写 core 模块 + 前端组件 |
| 要诊断一个 bug | 需排除: 插件是否注册 → flag 是否启用 → manifest 是否正确 → middleware 顺序是否正确 → core 逻辑本身 | 直接定位 core 逻辑 |
| 要写测试 | 需 mock PluginManager、mock manifest 响应 | 直接测试纯函数 |

当前的认知开销对两个开发者以上的团队会产生明显的摩擦损耗。

## 三、从产品视角看：用户真正需要的是什么？

我们替产品的利益相关者提几个问题：

### 3.1 护理教育者视角

```
Q: 我想为一个新病例启用情绪模拟，需要几步？
A: 1. 打开后台 → 2. 在病例配置中勾选"启用情绪模型" → 3. 保存
   代码层面：0 步。配置层面：1 步。
   （情绪作为一个"插件"开启，对教师是无感的——这正是配置驱动的正确做法）

Q: 同一个功能开启后，我需要知道"它是个插件"吗？
A: 完全不需要。教师只需要看见"有/没有情绪模拟"这个业务语义。
```

### 3.2 产品管理者视角

```
Q: 插件机制和点餐式功能配置，哪个更接近业务现实？
A: 在教学场景中，教师关心的是"我的课堂需要哪些教学工具"，不是"哪些插件已注册"。

Q: 如果我们要向第三方开放这个平台，当前机制够用吗？
A: 不够。当前的目录扫描 + 约定接口距离一个真正稳定的 SPI 还有 gap：
   - 没有版本化声明
   - 没有沙箱隔离
   - 没有权限模型
   - 没有正式发布/弃用周期
```

### 3.3 运维者视角

```
Q: 插件失败了会怎样？
A: emotion 的 middleware 有 try/except 包住，其他没有。一个插件崩溃可能拖垮整个 pipeline。

Q: 我怎么知道系统目前启用了哪些插件？
A: 通过 /api/admin/plugins 端点查看——但该端点未做分页、未做搜索结果、未告知影响范围。
```

## 四、演进方向的战略判断

### 4.1 核心主张

**"插件"这个抽象在这个阶段是错误的优先级。**

当前系统的真实需求按优先级排列：

```
高优先级 ┌──────────────────────────────────────────────┐
         │  1. 病例配置驱动 → 按病例启用/禁用的功能开关    │
         │  2. 功能模块化 → 代码组织清晰，职责单一         │
         │  3. 可测试性 → 每个功能可独立验证              │
         ├──────────────────────────────────────────────┤
         │  4. 动态扩展 → 运行时发现并加载新功能 (插件)   │
中优先级  │  5. 第三方接入 → SPI + 沙箱 + 版本契约        │
         └──────────────────────────────────────────────┘
               低优先级
```

目前的插件系统投入了大量精力在 4 和 5 上，而 1、2、3 还在通过迂回的方式实现。

### 4.2 建议方向：从"插件协议"转向"功能模块化配置"

```
现在（Plugin Protocol）     →    未来（Feature Modules + Config）

Plugin ABC 类               →  FeatureModule dataclass / 配置项
PluginManager.discover()    →  显式功能注册表
importlib 扫描              →  import 语句（IDE 可追踪）
ui_manifest()               → 前端显式 feature → component 映射
PipelineStage.PLUGIN_EARLY  → PipelineStage 保留，middleware 直接注册
NoteSource 作为扩展点       → 保留，这是唯一真正需要抽象的地方
```

这种转变带来的核心收益：

1. **可追溯性**：`Ctrl+点击` 功能开关 → 直接跳到实现代码，不是跳到一个插件的空壳
2. **确定性**：启动时就知道有哪些功能，不是运行时扫描
3. **架构清晰度**：配置的归配置，代码的归代码
4. **入门成本**：新开发者不需要理解"插件协议"来找一个功能的入口

### 4.3 一种参考架构：配置驱动功能矩阵

```yaml
# 伪代码 · 病例配置中的功能声明
features:
  emotion: true               # 启用情绪模型
  patient_initiative: true    # 启用主动追问
  physical_exam: true         # 启用查体面板
  pause_enabled: false        # 不允许暂停
```

```typescript
// 伪代码 · 前端功能-组件的显式映射
const FEATURE_TABS: Record<string, TabDef[]> = {
  emotion: [{ icon: Smile, component: EmotionTab, priority: 5 }],
  physical_exam: [{ icon: Stethoscope, component: ExamPanel, priority: 3 }],
  '!physical_exam': [],  // 清空覆盖
};

// Pipeline middlewares 为显示注册
core_middlewares: [
  phase_guard,
  phase_transition,
  prompt_builder,
  llm_caller,
  emotion_tracker,        // 直接注册，不经过插件层
  persister,
  side_effects,
]
```

这个模式的优势：
- 配置在 YAML/JSON/Dict 中完成，非开发者也可以参与
- 组件树由配置驱动，不需要 runtime scan
- `emotion_tracker` 和 `phase_guard` 是平等的 pipeline 成员，没有"第三方插件"和"核心中间件"的区别
- 回顾这个系统在业务维度的本质——它是一个 CASE 编辑器 + 运行时引擎，不是 CMS 插件市场

### 4.4 什么情况下应该保留"真·插件系统"

只有当系统面临以下至少两个条件时，才需要真正的插件架构：

1. **有第三方独立开发者/团队** 在为本系统开发扩展，且他们无法修改核心代码
2. **扩展需要编排多个生命周期事件**（不仅仅是中间件，还包括数据迁移、后台任务、仪表板等）
3. **扩展数量达到 20+**，无法在核心代码中维护
4. **需要支持热加载/热替换** 即不停机更新功能

当前系统不满足上述任何条件。

### 5.1 短期（当前 Sprint ~ 下个 Sprint）

```

动作：
  □ emotion   → 核心 pipeline middleware（当前分析 → 直接提交）
  □ exam_emotion_bridge → 合并入 emotion flag
  □ 拆除 nursing-record / questionnaire 的后端空壳插件类
产出：-800 行代码，零行为变更
```

### 5.2 中期（本季度内）

```
目标：建立清晰的"功能模块"体系
动作：
  □ 定义 FeatureModule 类型协议（取代 Plugin ABC）
  □ 前端建立显式 Tab/Overlay 声明清单（取代 import.meta.glob 扫描）
  □ 后端 pipeline 中间件直接注册（取代 PluginManager.build_pipeline）
  □ 合并 PluginRegistry 的功能到 TrainingEngine 本地状态管理
产出：隐式协议 → 显式注册，构建时确定性替代运行时发现
```

### 5.3 长期（下个季度及之后）

```
目标：平台化准备
动作：
  □ 如果确定需要第三方扩展 → 设计真正的 SPI（版本化 + 沙箱 + 依赖注入）
  □ 如果不确定 → 保持简单，仅在确实需要时引入复杂度
  □ 完善病例配置系统，使"功能组合"在配置层面即可完成
产出：一个明确的决策——要么没有插件系统，要么有一个真正的插件系统
```

## 六、总结

### 6.1 一句话判断

> 当前的插件系统是一个**过早泛化的抽象**——它用一个完整的插件协议解决了一个"功能开关 + UI 注册"的问题，而后者用配置驱动 + 显式注册就能以十分之一的成本实现。

### 6.2 三个关键洞察

1. **配置 ≠ 扩展**：病例配置（是什么教学场景）和代码扩展（由谁增加功能）是正交问题，不应耦合在同一机制中
2. **双端验证是负债**：前后端各自维护一份 flag 过滤逻辑，首次成为 bug 来源，其次才是维护成本
3. **抽象的正确时机**：等到真正有第三方接入需求时再引入插件系统，比现在维护一个不合格的抽象要经济得多

### 6.3 推荐行动

| # | 行动 | 影响 | 风险 | 工作量 |
|---|---|---|---|---|
| 1 | emotion 吸收为核心 middleware | 低（行为不变） | 极低 | 1天 |
| 2 | 拆除后端空壳插件类 | 中（减少 800 行） | 低 | 0.5天 |
| 3 | 前端显式注册替代 import.meta.glob | 中（构建优化） | 中（需验证所有 Tab） | 1天 |
| 4 | 定义 FeatureModule 协议取代 Plugin ABC | 高（架构升级） | 中（变更范围较大） | 2-3天 |
| 5 | PluginManager 废弃 | 高（架构重塑） | 高（需审核调用方） | 1-2天 |

**建议路径**：1 → 2 → 3 → 4+5（逐步推进，每步可逆）
