## 一、这是什么

护理学生的**虚拟患者问诊训练**。学生在一个会话里与 LLM 扮演的患者对话、做床旁检查、填写护理记录、交卷，
然后看逐项评分与证据。单人维护、实验性产品，正在准备一次**系统可用性评价（SUS）**研究，因此界面的
首因印象与可理解性直接决定研究数据。

一次训练的任务链：`了解任务 → 采集病史（对话） → 床旁查体 → 写护理记录 → 交卷 → 看评分 → 复盘 → 问卷`。

## 四、本次已经做过的结构改动（避免重复建议）

1. 删除对话列里的「完成度条」（同一件事曾同时出现在顶栏、对话列、开场卡三处）；门禁现在只有一处：
   顶栏「结束训练」按钮上的未满足数字 + 点开后弹窗里的逐条清单。
2. 开场从六段说明文字缩成**任务卡**：角色一行 + 步骤芯片 + 缺什么 + 建议开场；
   「要交什么 / 如何交卷 / 结束后看什么」搬进交卷弹窗。
3. 输入区从「无边框 textarea + 框外两个按钮」换成 Mantine `Textarea`（autosize + 左右插槽，边框/焦点环开箱即用）。
4. 患者区从「可折叠 280px 大图卡 / 88px 窄条两套状态」改成「桌面 216px 常驻列 + 手机 56px 条 + 大图按需浮层」。
5. 工具列删掉图标下那行 9px 状态小字（改为状态点 + tooltip/无障碍名）；问诊清单入口不再在工具列重复（归患者卡的进度 chip）。
6. 桌面面板从「挤压对话列」改成 Mantine Drawer 覆盖；面板下移到顶栏之下（顶栏保持可用）。

## 六、硬约束（方案必须落在这些之内）

1. **状态不得新增来源**：完成条件、可用性、产物状态、动作可用性全部来自服务端 manifest；前端不推导。
   改动可以改"怎么显示"，不能改"谁来决定"。
2. **Mantine 9.6.3 已全局配置**（`MantineProvider` + 自定义 `brand` 色阶 + 暗色模式 + 中文字体栈）。
   方案应优先使用 Mantine 组件与 style props；不引入第二套 UI 库或自研动画引擎。
3. **无障碍**：触摸目标 ≥44px；`aria-label` 已被测试与辅助技术依赖（如「护理记录（草稿未提交）」）。
4. **测试环境是 jsdom（无排版引擎）**：`getBoundingClientRect` 恒为 0，因此自动化测试只能断言"声明的值"
   （宽高、属性、文案）；像素级效果必须由人在浏览器确认。
5. **视口目标**：390×844（竖屏手机）、844×390（横屏手机）、1440×900（桌面）；暗色态同样要有结论。
6. **单人维护**：不接受需要长期照料的复杂依赖、设计系统生成器或大规模重构。

## 七、请评估者交付什么

1. **诊断**：按「影响学生完成任务 / 影响数据可信度 / 纯观感」三档排序，指出上表之外的遗漏（可反驳）。
2. **信息架构方案**：桌面与移动各一张线框（ASCII/mermaid 均可），说明为何优于现状；**至少两个方向**并给取舍。
3. **组件级规格**：具体到 Mantine 组件与 props，给出字号/行高/间距/圆角/颜色 token 与各状态
   （默认/悬停/激活/禁用/加载/空/错误）。
4. **响应式规则**：窄屏与矮视口的降级顺序（先牺牲什么、绝不舍弃什么）。
5. **实施顺序**：按"改动小、观感收益大"排序，并标注哪些改动会触及契约或测试。
6. **明确不做**：不新增状态源、不改评分/门禁语义、不引入图表或动画库、不重写交互协议。
