# 测试核对单规范

本文件规定核对单的生成标准。**所有测试在正式测试服（https://test.205716.xyz）上进行**，核对单面向非技术背景的测试员。

---

## 一、何时需要测试

**需要测试**（必须生成核对项）：
- 新增页面、弹窗、按钮、表单等可见界面
- 修改现有功能的操作流程（如点击步骤变化）
- 修复用户能看到的错误（显示不对、操作卡住、数据不对）
- 权限或角色改动影响用户能做的操作

**不需要测试**（文件内容写 `无需测试`）：
- 系统内部调整（用户操作和界面无变化）
- 自动部署流程变更
- 文档更新
- 代码格式整理
- 底层软件版本更新（不影响用户可见功能）
- 日志、监控等后台配置

**判断原则**：一个不懂代码的人，打开测试服网站后，能否"看到"或"用出"这次改动？能→需要测试；不能→无需测试。

---

## 二、统一用语

- 版本无用户可见变更：文件内容仅一行 `无需测试`

---

## 三、操作步骤写作规范

### 原则
- 每条核对项一行操作，用 `→` 串联步骤
- 使用页面上实际出现的文字（按钮名、菜单名、标签名）
- 从角色视角描述，如"学生登录 → 开始训练 → ..."
- 禁止使用技术术语（路由、组件、接口、API、渲染等）
- 预期结果描述"看到什么"，不描述"系统内部做了什么"

### 示例

**好**（简单明了）：
```
### 1. 学生训练中新增体格检查
**操作**: 学生登录 → 开始训练 → 点击工具栏「体格检查」→ 选择「胸部」→ 点击「执行检查」→ 观察对话区
**预期**: 对话区出现系统消息，包含胸部听诊和叩诊检查结果
```

**坏**（技术术语太多）：
```
❌ 1. 进入 /training 页面 → 调用体格检查 API → 查看 response
   预期: 组件正常渲染
```

### 格式规则
- 操作步骤用 `→` 串联，一行写完
- 预期结果描述"看到什么"
- 若涉及多个角色（如学生操作后教师确认），拆为两个独立的核对项
- 禁止出现：路由路径、API 名称、组件名、commit hash 等

---

## 四、核对单文件模板

```markdown
# {stag_ver} 测试清单

**版本**: v{prod_ver} → {stag_ver}
**环境**: https://test.205716.xyz

### 1. {功能名称}
**操作**: {步骤简述，用 → 连接}
**预期**: {可见的预期结果}
```

模板说明：
- 无测试账户——已预先告知
- 无通过/失败勾选框——口头反馈即可
- 核对项仅包含本次版本特有变更，不罗列已有功能
- 无用户可见变更时，文件内容仅一行：`无需测试`
